# Channel adaptation

These are editorial starting points, not API capability promises. Check the connected account and current official requirements for the selected format. Do not hardcode evolving limits here.

| Destination | Useful starting treatment | Checks before preparation/delivery |
| --- | --- | --- |
| X | Compact project claim + visible proof + credits/link | Account limits, video/image requirements, handles, standalone post versus thread |
| LinkedIn | What was built, why the workflow matters, concrete result | Profile/page destination, media/document support, mentions and link placement |
| Instagram | Demonstration or product state; concise headline and caption | Reel/feed/story distinction, framing/safe areas, cover, account publishing mode |
| TikTok | Immediate demonstration, clear context and short explanation | Connected account's direct publishing/metadata requirements and framing |
| YouTube | A demonstration with a useful title and description | Short versus regular video, title/privacy/category requirements |
| Threads / Bluesky / Mastodon | A concise finding with a fitting proof artifact | Platform-specific length, mentions, links and media support |
| Pinterest | A durable visual idea with descriptive copy and destination | Board, title, link and media requirements |
| Other connected channels | Choose from the user's actual goal and audience | Verify service/format availability instead of assuming parity |

One source can produce several variants, but each destination has a separate approved package and delivery receipt. Do not mechanically duplicate the same caption or force a vertical video on every channel. If the user asks only for one channel, finish that channel without expanding delivery scope.

A service returned by Buffer's channel query is evidence of a connection, not proof that a particular format can publish. See [Buffer's reference](https://developers.buffer.com/reference.html) and the destination's official documentation before assembling its metadata.
